## 1. Текущее состояние (что есть)

- **Просмотр**: статический сайт (nginx из тома `redpen_public`, наполняется контейнером `content-sync` из git-репозитория `redpen-publish`). Аннотации — JSON-файлы per-page.
- **Редактор**: включается `?editor=1`; панель на vanilla JS (`redpen-editor-panel.js` + `redpen-editor-bootstrap.js`). «Показать» — локальный предпросмотр, «Отправить» — POST/PUT на `api.medinsky.net/api/editor/{docId}/{pageNum}`.
- **Бэкенд**: FastAPI, файловое хранилище (`storage.py`), страницы пишутся в `STORAGE_DIR=/var/redpen-data` (примонтированный `./redpen-publish` на сервере).
- **Аутентификация**: вход по личному токену → серверная сессия в памяти + cookie `redpen_session`. CSRF-токен выдаётся эндпоинтом `/api/auth/csrf`.

### Архитектурные

- **A1. Два источника правды.** Канонический контент — markdown в `redpen-content` (конвертируется в JSON при сборке), но редактор пишет JSON напрямую в `redpen-publish`. Любая пересборка (`build_website.py` / rebuild-эндпоинт / content-sync) может молча затереть правки редактора.
- **A2. Правки редактора не попадают на сайт.** API пишет в примонтированный `./redpen-publish` (рабочая копия в `/root/apps/redpen/infra`), а nginx отдаёт том `redpen_public`, который наполняется content-sync из GitHub. Т.е. «Отправить» сохраняет на диск сервера, но посетители изменений не видят, пока кто-то не закоммитит/запушит и не перезапустит content-sync.
- **A3. Rebuild-эндпоинт пишет в эфемерный путь.** `POST /api/rebuild/...` пишет в `/app/redpen-publish/...` внутри контейнера — это build-time копия, не примонтированный том; результат исчезает при пересоздании контейнера.
- **A4. Optimistic locking не реализован.** Клиент шлёт `clientPageSha`, сервер его игнорирует — 409 не возвращается никогда, конфликтующие правки молча теряются (клиентский код обработки 409 при этом уже написан).
- **A5. Нет атрибуции и истории.** У аннотации нет автора, дат создания/изменения, версий; нет DELETE (ни на сервере, ни в UI); нет статусов (черновик/опубликовано).

### UX / мелочи

- Логин — модалка «введите личный токен»; нет индикации «кто я», нет выхода.
- `alert('Сохранено')` / `alert('Отправлено')` вместо ненавязчивых уведомлений.
- Отладочные `console.log` (✅ ЛОГ A…K) в продовом коде.
- Нет удаления аннотации, нет списка аннотаций страницы в панели, маркер нельзя перетащить.
- Нет предупреждения `beforeunload` при уходе со страницы с несохранённой формой (защита есть только внутри редактора).

## 3. Целевая архитектура

### Жёсткое ограничение: сайт остаётся полностью статическим

Собранный сайт (`redpen-publish` / содержимое `redpen_public`) — самодостаточный
набор файлов: его можно раздавать как статику, копировать на флешку, упаковывать
в простое приложение как контент, открывать офлайн. Из этого следуют правила,
которые обязана соблюдать любая доработка:

- **Просмотрщик никогда не ходит в API.** Аннотации, текст, изображения — только
  статические файлы по относительным путям. API нужен исключительно редактору
  (`?editor=1`) и кабинету; без сети деградирует только редактирование.
- **БД — деталь реализации бэкенда редактирования**, а не рантайм-зависимость
  сайта. Публикация из БД всегда материализуется в те же per-page JSON-файлы.
- Каждое изменение через редактор завершается перегенерацией статического
  снапшота — каталог сайта в любой момент целостен и переносим.

**Принцип: единый источник правды для аннотаций — база на сервере; статика — только рендер.**

```
Пользователь ──Google Sign-In──▶ API (FastAPI)
                                   │  users, sessions, annotations,
                                   │  history — SQLite (том redpen_db)
Просмотр (nginx) ◀── публикация ───┘
   статика: изображения, текст,    annotations/*.json перегенерируются
   аннотации (JSON-снапшоты из БД)  в redpen_public при каждом изменении;
                                    сайт БД не видит и работает без API
```

- **SQLite** (файл на отдельном томе) вместо россыпи JSON как канонического хранилища: даёт атомарность, авторство, историю, выборки для кабинета. JSON per-page остаётся форматом *публикации* — API после каждого изменения атомарно перегенерирует `page_NNN.json` прямо в том `redpen_public` (примонтировать его в api). Тогда правка видна на сайте сразу, без git-цикла, а content-sync продолжает обновлять только изображения/текст/код.
- Markdown-файлы аннотаций в `redpen-content` объявляются архивом/сырьём для первичного импорта, дальше не редактируются (однократная миграция md → БД).
- **Аутентификация — Google Identity Services (кнопка "Sign in with Google")**: фронт получает ID-token (JWT), шлёт на `POST /api/auth/google`, сервер верифицирует подпись библиотекой `google-auth` (audience = наш client_id), находит/создаёт пользователя, выдаёт сессионную cookie. Полный OAuth-flow с redirect не нужен — сайт статический, GIS-кнопка проще и безопаснее. `medinsky.net` и `api.medinsky.net` — same-site, поэтому cookie `SameSite=Lax; Secure; HttpOnly; Domain=.medinsky.net` работает без хаков.
- **Роли**: `admin` / `editor` / `viewer`. Войти через Google может кто угодно, но право записи получают только адреса из allowlist (таблица в БД, управляется админом из кабинета). Токен-вход остаётся как dev-fallback, токены — в env/секретах, не в коде.

## 4. Поэтапный план

### Этап 0 — Заткнуть дыры (без новых фич, ~1 день)

1. Требовать валидную сессию во всех write-эндпоинтах (`Depends(require_user)`), 401 иначе — клиентская обработка 401 уже есть.
2. Реально проверять CSRF: сверять `X-CSRF-Token` с cookie (double-submit, cookie не httponly) — или отложить до Этапа 1, ограничившись `SameSite=Lax` + строгим CORS.
3. Вынести `VALID_TOKENS` в переменную окружения / `.env.secrets`; убрать из git-истории ротацией токенов.
4. Закрыть `/logs`, `/api/logs` за сессией с ролью admin; убрать логирование списка валидных токенов.
5. `CORS_ALLOW_ORIGINS=https://medinsky.net` на проде (env уже поддерживает).
6. Включить optimistic locking: сравнивать `clientPageSha` с текущим `serverPageSha`, отвечать 409 (клиент уже готов).
7. Убрать отладочные `console.log` из bootstrap.js.
