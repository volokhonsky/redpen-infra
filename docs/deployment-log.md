### Расхождение с планом: топология `redpen-publish` на сервере

Runbook предполагал, что `/root/apps/redpen/infra/redpen-publish` (bind-mount
`STORAGE_DIR` в api) — git-клон с полным контентом. По факту это **не git-репозиторий**,
а маленькая директория-заглушка от старого API (единственный файл —
протухший `page_007.json` с `annotations: []`, самим API же и созданный при
первом `GET` до этапа 2). Настоящий опубликованный контент (449 файлов)
живёт (а) в самом `/root/apps/redpen/infra` (это отдельный git-клон
`redpen-publish.git`, использованный при первичном разворачивании инфры) и
(б) в volume `redpen_public` (`/srv/public`), который наполняет `content-sync`
из своего собственного клона в `/srv/repo`.

Из-за этого адаптировал два шага рантбука:
- **Импорт**: не из `/var/redpen-data` (там было почти пусто), а из
  `/srv/public` (после того как в `docker-compose.yml` добавился том
  `redpen_public:/srv/public` в сервис `api`) — это и есть текущий живой
  контент. `docker exec redpen-api-1 python scripts/api/import_annotations.py /srv/public`
  → `docs=1 pages=449 imported=33 skipped=0 errors=0`.
- **Экспорт снапшота в git**: `export_annotations.py --to /var/redpen-data`
  (как в плане) → затем вручную скопировал получившиеся файлы в
  git-репозиторий (`/root/apps/redpen/infra` на сервере не смог запушить —
  его deploy-ключ read-only; закоммитил и запушил из локального клона
  `redpen-publish/` на своей машине, коммит `c10f55a`). Разница — 2 файла
  (`page_017.json`, `page_204.json`): аннотациям с пустым `id` в исходном
  контенте импорт присвоил `srv-import-<hex>`, остальное не изменилось.

### Найденный и исправленный на лету баг: права 600 на публикуемых файлах

`publisher.py` (и `export_annotations.py`) писали через `tempfile.mkstemp()`
(режим 0600, только владелец) и `os.replace` — атомарно, но без `chmod`.
Пока запись шла в `STORAGE_DIR` (никогда не раздавался nginx напрямую), это
было незаметно. Как только `PUBLISH_DIR=/srv/public` (тот же volume, что
раздаёт `frontend`/nginx) — republish 15 существующих страниц при первом
`publish_all()` на старте **тут же дал 403 на живом сайте**
(`medinsky.net/medinsky11klass/annotations/page_007.json` и другие).
Пофиксил (`os.chmod(tmp_path, 0o644)` перед `os.replace`), задеплоил
отдельным циклом `scp` + `docker compose up -d --build api` **до** продолжения
рантбука, добавил regression-тесты (`test_publish_page_writes_world_readable_file`,
аналог в `test_export_annotations.py`), коммит `5c55df2`. Проверено: файлы
снова 644, `curl` → 200 по всей книге (выборочно проверил 001/006/007/008/020/100/200/300/400).

Тот же паттерн (`mkstemp` без `chmod`) есть и в `storage.py::save_inbox` —
не трогал (не раздаётся nginx, ниже приоритет), но стоит поправить отдельно.

## 2026-08-20 — фикс бага №2: правка опубликованной аннотации создавала дубликат

Симптом: в редакторе клик по **опубликованному** маркеру → правка текста →
сохранение создавало новую аннотацию вместо обновления существующей. Ровно тот
путь, которым естественно править текст комментария.

Причина: `annotations.js` рендерит опубликованные маркеры с DOM-id
`'circle-' + a.id`, а редактор читал `el.id` дословно — в `handleMarkerClick`
и в `snapshotDomMarkersToState`. Префикс уезжал в `draft.id` и дальше в
`PUT /api/editor/<doc>/<page>/circle-<annId>`; PUT «создаёт, если id нет» —
рядом появлялась вторая строка.

Сделано:
1. **Код** (только `templates/js/redpen-editor-bootstrap.js`, API и БД не
   тронуты): добавлен `annIdFromDom()` — единая точка нормализации; через неё
   идут `handleMarkerClick` и `snapshotDomMarkersToState`, так что id в
   состоянии редактора всегда серверные. Симметрично `markers.upsert()` и
   удаление старого узла ищут элемент с фолбэком на `'circle-'+id` — без этого
   чистый id рисовал бы второй кружок поверх существующего. В deep-link
   (`?ann=`) убрано двойное сравнение, ставшее ненужным. `node --check` чисто,
   `pytest` — 345 passed.
2. **Выкладка точечная, без `build_website.py`.** Скопирован один файл в клон
   `redpen-publish` (по нему клон и `templates/` расходились ровно на фикс),
   коммит `6582d12`, push, `docker restart redpen-content-sync-1` →
   `Publish complete`. Коммит в infra — `92a94db`.
3. **Проверка на живом сайте**: `curl https://medinsky.net/js/redpen-editor-bootstrap.js`
   — `annIdFromDom` на месте. На `document_index.html?page=8&editor=1` DOM-id
   остались `circle-ann-p008-1`, а `st.page.annotations` — `ann-p008-1`; клик по
   опубликованному маркеру даёт `draft.id = "ann-p008-1"`, режим `existing`,
   число кружков не растёт. Локально (с перехваченным `fetch`) сохранение уходит
   как `PUT /api/editor/medinsky11klass/008/ann-p008-1` — без префикса.
4. **Дубликатов в БД нет**: `SELECT ... FROM annotations WHERE ann_id LIKE
   'circle-%'` на проде — 0 строк. Уборка не потребовалась, бэкап БД для этой
   выкладки не делался (данные не затрагивались).

Грабли на будущее:
- Полную пересборку сайта здесь сознательно **не** запускали: она
  перегенерирует 448 постраничных HTML из аннотаций, лежащих в локальном клоне,
  а канон — БД на проде. Для правки одного JS точечная копия файла безопаснее;
  полный `build_website.py` уместен только после синхронизации рендера с прода.
- `redpen-editor-bootstrap.js` подключается **без** `?v=` (в отличие от
  `main.js?v=tags-1`), так что у открытых вкладок редактора фикс появится
  только после перезагрузки; `Cache-Control` nginx не шлёт, ревалидация идёт по
  etag/last-modified, поэтому обычного обновления страницы достаточно.

### 2026-08-21, вдогонку — кэш браузера

Пользователь сообщил, что `?only=` показывает все комментарии и нет цветов
категорий. В чистом браузере страница отрабатывала правильно (один маркер
`circle--cat-evidence`, одна карточка) — дело было в кэше.

Причина глубже единичного случая: у образа `nginx:alpine` нет никакого
`Cache-Control`, и браузер кэширует **эвристически** — обычно 10 % от возраста
файла. Имена файлов не содержат хэша, так что после любой выкладки читатель мог
неопределённо долго сидеть на старом `page-view.js` и не видеть ни новых
комментариев, ни цветов. То есть до сих пор каждая выкладка фронтенда доезжала
до читателей «когда-нибудь».

Добавлен `frontend/default.conf`: `no-cache` (обязательная ревалидация, ETag
превращает её в 304) для html, js, css и `annotations/*.json`; сканы страниц и
шрифты — `public, max-age=604800`. Грабля при выкладке: контекст сборки у
сервиса `frontend` — корень infra, поэтому `COPY` нужен с путём `frontend/…`.

Проверено: заголовки на месте, повторный запрос с `If-None-Match` даёт 304,
сайт и кабинет отвечают 200.

### 2026-08-21, вдогонку 2 — образ API и сходимость снапшота

**Грабля: `scp` в контекст сборки не меняет работающий контейнер.** Файлы
`scripts/` копируются в образ API на сборке, поэтому выложенный по scp
`page_html.py` в контейнер не попал: API продолжал рисовать страницы старым
кодом (без заголовка `AUTO-GENERATED`), а ночной снапшот исправно уносил это в
git. Лечится пересборкой (`docker compose up -d --build api`) — она нужна после
любого scp в `scripts/`, а не только при правке `scripts/api/`.

**Сходимость цикла «правка → том → git → синк → том».** После пересборки
проверено: `publish_all` → 315 страниц, `failed=0`; снапшот уносит изменения;
повторный прогон — «изменений нет». Затем перезапуск content-sync (то есть
полная выкладка контента) и снова снапшот: цикл сходится за один коммит и
дальше стоит на месте. Права на `pages/` и `annotations/` переживают
синхронизацию (uid 10001).

**Осадок, который стоит убрать позже.** Тот единственный коммит после синка —
внедрение `<script src="/app-config.js"></script>` в страницы: content-sync
делает это при публикации, а снапшот уносит результат обратно в git. Работе не
мешает (просмотрщик к API не обращается, ссылка просто не используется), но это
артефакт развёртывания в исходном снапшоте, и для офлайн-архива абсолютный путь
`/app-config.js` не разрешится. Правильнее не внедрять его в `pages/*` вовсе —
он нужен только SPA и кабинету.

## 2026-08-23 — /app/ на прод и разбор устойчивости к заливу

Выложено: приложение `/app/` (карточка комментария), `?only=` с раскрытием,
эндпоинт `GET /api/annotations/{docId}/{pageKey}/{annId}`, ограничение частоты

### Про опасение «падение /app/ положит весь сайт»

Проверено — в такой формулировке этого случиться не может, но чутьё указывало
на реальную связь, просто в другом месте.

`/app/` и `/cabinet/` — **статические файлы**, которые nginx отдаёт из тома.
Серверного приложения за ними нет: запрос `/app/` стоит ровно столько же,
сколько любая страница. Падать там нечему. И сайт читателя **не обращается к API
вовсе** (инвариант офлайна), поэтому даже полностью выведенный из строя API
читателя не касается — ровно ради этого инвариант и держат.

Настоящая связь — **Caddy**: он один на оба хоста, и залив по `api.medinsky.net`
тратит его соединения и процессор, а с ними и способность отдавать сайт. Плюс
API — **один процесс uvicorn** (`workers=1`) с глобальным замком вокруг SQLite:
насытить его несложно.

### Что сделано

- **Ограничение частоты в самом API** (`scripts/api/ratelimit.py`, «дырявое
  ведро» на адрес, без зависимостей и фоновых потоков). Два предела: общий
  240/мин (живой редактор шлёт десятки запросов на страницу) и жёсткий 12/мин
  для `/api/auth/google` и `/api/auth/login` — проверка Google-токена ходит в
  сеть и считает подпись, то есть это самая дорогая ручка, открытая всем.
  `/api/health` не ограничивается: глушить проверку живости значит ослепнуть
  ровно тогда, когда что-то происходит. Проверено на проде: шесть попыток входа
  проходят, дальше 429; health держит 15 подряд.
- **Предел на тело запроса — 2 МБ** (Caddy, хост API). Без него один
  гигабайтный POST на открытую ручку дороже тысячи мелких: FastAPI читает тело
  в память целиком, а ограничитель считает такой запрос за один. Проверено: 413.
- **Логи Caddy с `debug` на `info`**, хранение ограничено объёмом и сроком
  (5 МБ × 2, 168 ч). Отладка сертификатов давно закончилась, а логи содержат
  адреса посетителей — `docs/anonymity-model.md` прямо требует сократить их
  хранение. Файл к этому моменту вырос до 7,1 МБ.

### Найдено и исправлено попутно: сломанный предпросмотр

`X-Frame-Options: DENY` на хосте сайта запрещал кадрирование **вообще, включая
собственные страницы**, — то есть предпросмотр в только что выложенном `/app/`
на проде не работал бы (локально это не проявлялось: dev-сервер такого
заголовка не шлёт). Заменено на `SAMEORIGIN` плюс `Content-Security-Policy:
frame-ancestors 'self'`. Чужим сайтам кадрирование по-прежнему запрещено, у
хоста API остался `DENY`.

### Что осталось риском

- **Один рабочий процесс API.** Больше воркеров дали бы устойчивость, но у нас
  SQLite с модульным соединением и глобальным замком, плюс публикатор пишет
  файлы — переводить на несколько процессов вслепую нельзя.
- **У Caddy нет ограничения частоты** (плагина в сборке нет), так что залив
  по-прежнему тратит его ресурсы до того, как дойдёт до нашего ограничителя.
  Полное лечение — Cloudflare или подобный слой перед сервером.
- Легаси `GET /api/pages/{pageId}` открыт всем и ходит в БД. Удалять рано: им
  пользуется старый SPA-редактор, который уйдёт вместе с ним (Ф6).

Отключается `--no-sections`, вид сегмента меняется `--section-prefix`.

### Дозаливка того же вечера: предпросмотр редактора больше не считается чтением

Проверка «а точно ли следы редактора не попадают в аналитику» нашла дыру.
Пути `/app/`, `/cabinet/`, `/api/` и `?editor=1` отбрасывались с самого начала,
но **предпросмотр в `/app/` грузит в iframe настоящую страницу читателя**
(`templates/app/app.js`: `'../' + docId + '/pages/' + label + '/?only=' + id`).
По адресу такой запрос неотличим от чтения — и хуже того, он с `?only=`, то есть
разбор комментария засчитывался бы как пересылку и портил единственную метрику,
которая говорит, что читателям пересылают.

Отличает его `Referer`: у навигации в iframe там адрес объемлющей страницы, а
`Referrer-Policy: no-referrer-when-downgrade` внутри https его сохраняет.
Добавлена проверка `analytics.private_referer` — в экспорт для Matomo и в
счётчики. Тестов стало 545.

Проверено на проде: из пяти запросов «как редактор» (`/app/`, `/cabinet/`,
предпросмотр страницы и предпросмотр с `?only=`) до Matomo не дошёл ни один, а
тот же самый адрес со ссылкой из Telegram — дошёл. Проверочный трафик снова
пропущен мимо обеих баз сдвигом позиции; дашборд остаётся с нуля.

Тогда же появился раздел 11 в `docs/server-setup-guide.md` — воспроизводимая

ссылкой на неё: две копии одних и тех же шагов разъезжаются.

### Что осталось

- **Архивация отчётов** идёт по обращению из браузера (умолчание Matomo). Для
  большого объёма правильнее `core:archive` кроном — сейчас сайт маленький,
  и это не срочно.
- **Настройки приватности Matomo** (обезличивание адресов, срок хранения сырых
  визитов) выставляет владелец в интерфейсе; по умолчанию Matomo хранит больше,

## 2026-08-24 — дашборд аналитики наружу: stats.medinsky.net

Раньше Matomo слушал только `127.0.0.1:8081` и открывался пробросом ssh. По
просьбе владельца выставлен наружу — на отдельном хосте и под двумя замками.

### Почему два замка

Снаружи Matomo — это не только форма входа, но и **ручка трекера**, доступная
всем желающим налить выдуманных визитов, плюс PHP-админка над базой, где лежат
адреса читателей. `basic_auth` в Caddy отсекает запрос до того, как он дойдёт до
PHP. Импорт логов идёт по внутренней сети docker (`http://matomo/`) и пароля не
видит — проверено прогоном крона после включения.

Ослабление осознанное и записано в `docs/anonymity-model.md`: раньше снаружи не
было видно ничего, теперь есть дверь.

### Что сделано

- DNS: `stats` → 70.34.202.231, **без прокси Cloudflare** (как остальные хосты).
- Блок хоста в `caddy/Caddyfile`: `basic_auth`, `reverse_proxy matomo:80`,
  заголовки безопасности, `Referrer-Policy: no-referrer` и
  `X-Robots-Tag: noindex, nofollow, noarchive`.
- `/root/apps/redpen/infra/.env.stats` (600) с хостом, логином и bcrypt-хешем;
  подключён к сервису `caddy` через `env_file` — отдельно от `.env.secrets`,
  которому в контейнере Caddy делать нечего.
- Matomo за прокси: `trusted_hosts[] = "stats.medinsky.net"` и
  `assume_secure_protocol = 1` в `config.ini.php` (бэкап рядом).

### Грабля: docker compose съедает `$` в bcrypt-хеше

`docker compose` **интерполирует значения из `env_file`**, и хеш вида
`$2a$14$LhBjQ…` он принимает за подстановку переменной: до Caddy доезжает
огрызок, а пароль молча не работает. Поймано до запуска по предупреждению
`The "LhBjQ…" variable is not set` в выводе `docker compose config`.

Лечение — удвоить каждый `$` в файле (`$$2a$$14$$…`). Проверка после запуска:
