# Адресация и нумерация страниц: анализ и предложение

Дата: 2026-07-08. Проработка пункта из `TODO` («нумерация типа А1, A2, 1, 2, 3»).
**Статус: реализовано и на проде** (манифест `pages[{file,label}]`, `?p=<метка>`,
легаси `?page=N`; см. `docs/deployment-log.md`). Ниже — исходный дизайн-документ,
сохранён как обоснование принятых решений. Главное требование — **не сломать
текущее поведение**: существующие ссылки `?page=N`, работу редактора и офлайн-копии.

## 1. Как адресация работает сейчас

Сейчас в системе сосуществуют **три нумерации**:

1. **Файловая (физическая)**: `page_NNN` — имена файлов `images/page_NNN.png`,
   `annotations/page_NNN.json`, `text/page_NNN.json`. Есть «особые» файлы:
   `page_000`, `page_-01` (обложка/форзацы).
2. **Логическая (UI)**: `?page=N`, пагинация, поле «перейти к странице».
   `main.js` пересчитывает: `phys = pageNumbering.physicalStart + N - 1`
   (`loadPage`, `logicalFromPhysical`). Для `medinsky11klass` сейчас
   `physicalStart=1`, т.е. логическая и файловая совпадают.
3. **Печатная (книжная)**: номера страниц бумажного учебника, на которые
   ссылаются люди и оглавление (`chapters[].startPage` в metadata). Авторские
   id аннотаций указывают именно на неё: в файле `page_007.json` лежат
   `ann-page8-1...` — печатная страница 8 живёт в файле 007.

Наблюдения / проблемы:

- **P1. Файлы `page_000` и `page_-01` недостижимы в просмотрщике**: логическая
  нумерация начинается с 1 → `page_001`; «страниц до начала» просто не существует
  для UI (clamp в `clampPage` режет всё <1).
- **P2. Латентный баг редактора**: редактор берёт `pageNum` = **логический**
  номер (`window.currentPageNum`) и шлёт его в API, который делает
  `zfill(3)` и пишет файл `page_{логический}`. Просмотрщик же читает файл
  `page_{физический}`. Работает только потому, что сейчас `physicalStart=1`.
  Стоит `physicalStart` стать ≠ 1 — правки поедут в чужие файлы.
- **P3. Валидация API** (`_validate_page_num`: int 1–999) не принимает `000` и
  `-01` — эти страницы нельзя редактировать в принципе.
- ~~**P4. Корневой `redpen-publish/metadata.json` устарел**~~ (`totalPages: 10` при
  449 файлах; актуальный — в `medinsky11klass/metadata.json` с `totalPages: 448`).
  **Решено**: файл никем не читался (проверено grep'ом по `templates/` и
  `build_website.py`) — удалён (коммит `551a799` в `redpen-publish`, локально,
  ещё не запушен).
- **P5. Пользователь видит номер, не совпадающий с книгой** (сдвиг из-за
  обложки/титульных листов) — собственно исходная жалоба из `TODO`.
- В `medinsky11klass/metadata.json` уже есть зачаток решения: `specialPages:
  [{"id": "pageA1", "name": "Обложка", "physicalPage": 1}]` — сейчас никем
  не используется.

## 2. Требования к целевому решению

- Пользователь видит и вводит **печатные** номера: `A1, A2, …` для
  преднумерованных листов (обложка, титул, форзацы), затем `1, 2, 3…` в точном
  соответствии с бумажной книгой.
- Старые ссылки `?page=N` продолжают открывать **те же страницы, что и раньше**.
- Файлы **не переименовываем**: это сломало бы старые офлайн-копии, git-историю
  контента и все внутренние пути. (Вариант «перенумеровать файлы начисто»
  рассмотрен и отвергнут.)
- Статическое ограничение (см. `docs/README.md`): всё решение — данные в
  `metadata.json` + логика в JS; никакого API для просмотра.
- Редактор и API продолжают работать; заодно закрываем P2 и P3.

## 3. Предлагаемая схема: явный манифест страниц

### 3.1. Данные

В `metadata.json` документа добавляется массив-манифест (генерируется скриптом,
см. 3.4; порядок = порядок листания):

```json
"pages": [
  { "file": "page_-01", "label": "A1", "name": "Обложка" },
  { "file": "page_000", "label": "A2" },
  { "file": "page_001", "label": "1" },
  { "file": "page_002", "label": "2" },
  ...
]
```

- `file` — базовое имя файлов (картинка/аннотации/текст) без расширения;
- `label` — то, что видит и вводит пользователь (уникален в документе);
- `name` — опциональная подпись (для тултипов/оглавления).

`pageNumbering` остаётся в metadata как легаси-поле для fallback'а.

### 3.2. Просмотрщик (main.js) — с полным fallback'ом

- Внутренняя единица навигации — **порядковый индекс** в манифесте (1..N),
  фактически нынешняя «логическая страница».
- **Если `pages` в metadata нет — поведение бит-в-бит текущее** (арифметика
  с `physicalStart`). Это гарантия нулевой регрессии для документов, которые
  ещё не мигрированы.
- Новый канонический параметр адреса — `?p=<label>` (`?p=17`, `?p=A1`):
  резолвится через манифест. Пагинация и pushState начинают генерировать `?p=`.
- **Совместимость**: `?page=N` поддерживается всегда и резолвится по СТАРОЙ
  арифметике (`physicalStart + N - 1` → file), после чего адресная строка
  нормализуется в `?p=<label>` этого файла. Старые ссылки открывают прежние
  страницы, даже когда в манифест добавились A-страницы в начало.
- Пагинация показывает `label` (A1, A2, 1, 2 …), Prev/Next ходят по индексу
  манифеста; поле «перейти к странице» принимает label как строку
  (в т.ч. `a1` без регистра).
- Оглавление (`chapters[].startPage` — печатные номера) наконец можно
  прицепить к навигации: печатный номер == label числовых страниц.

### 3.3. Редактор и API (закрывает P2/P3)

- Редактор перестаёт передавать логический номер: `main.js` уже вычисляет
  `currentPageId` (`page_NNN`) — редактор берёт **файловый ключ** из него
  (`window.currentPageId`), а не `currentPageNum`. Семантика `{pageNum}` в
  `/api/editor/{docId}/{pageNum}` документируется как «файловый номер».
- Валидация API расширяется: ключ страницы — строка по маске
  `-?\d{1,3}` (принимает `006`, `000`, `-01`), нормализация — как в имени
  файла, без int-преобразования. Это синергия с этапом 2, где `page_num` в БД
  уже TEXT «как в имени файла» — менять схему БД не придётся.
- Ответные/публикуемые пути не меняются: `annotations/page_{key}.json`.

### 3.4. Генерация манифеста

Скрипт `scripts/generate_page_manifest.py`:

- вход: каталог документа + правило нумерации в `meta.json` контента
  (сколько преднумерованных листов, с какого файла начинается печатная «1» —
  фактически расширенный `pageNumbering`: `{"frontMatter": ["-01", "000"],
  "printedStartFile": "001", "printedStartNumber": 1}`);
- выход: секция `pages` в `metadata.json`;
- `build_website.py` вызывает генерацию при сборке; валидация: каждый `file`
  манифеста существует в `images/`, каждый файл `images/page_*` есть в
  манифесте (или явно в ignore-списке), labels уникальны.
- Заодно чинится P4 (корневой metadata.json либо регенерируется, либо
  помечается как неиспользуемый и удаляется).

## 5. Явно отвергнутые варианты

- **Переименование файлов в сквозную нумерацию** — ломает старые офлайн-копии,
  внешние ссылки на картинки, git-историю; выгода нулевая при наличии манифеста.
- **Смена семантики `?page=N` на «печатный номер»** — молча перенаправит все
  существующие ссылки на другие страницы; вместо этого вводим новый параметр `?p=`.
- **Держать соответствие в API/БД** — нарушает статическое ограничение
  (просмотрщику пришлось бы ходить в API за картой страниц).
