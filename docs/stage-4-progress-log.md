## 2026-08-21 — Ф1, часть 1: модель данных

### Источник категории (`category_source`, `category_set_by`)

Проблема, которую это чинит: колонка `category` не может ответить, разобрана ли
аннотация. Дефолт `other` означает одновременно честное «не приём, а пояснение»
(13 % корпуса — осознанное решение `annotation-classification-2026-08.md`) и
«никто этим не занимался». Вся приёмка держится ровно на этом различии.

- `annotations.category_source` — `default` | `tags-backfill` | `agent` | `human`,
  плюс `category_set_by` (кто назначил). Формат статики не тронут: поля служебные,
  в опубликованный JSON не попадают (тест).
- Источник едет **только вместе с явной категорией**: обычное сохранение текста
  из редактора не превращает догадку в решение человека. Явная категория без
  указания источника = решение человека (это путь редактора); CLI называют себя сами.
- `backfill_categories.py --only-default` теперь смотрит на источник, а не на
  значение. Раньше флаг затирал сознательно выбранное человеком «Прочее» —
  по значению оно неотличимо от неразобранного.
- `import_annotations.py` проставляет `agent`: импорт идёт из конвейера
  агента-аннотатора, значит категория в файле — машинное решение, ждущее приёмки.
- `GET /api/annotations` принимает `category` и `categorySource`. Это и есть
  вход очереди приёмки: `categorySource=default` — неразобранное,
  `categorySource=agent` — проверить решения агента.

### Ревизии

`annotation_history` была заготовкой журнала ревизий: полный снимок на каждую
мутацию в той же транзакции, снимок уже включал категорию, откат уже работал.
Достроено недостающее:

- колонки `rev_no`, `parent_rev_id`, `agent_run_id`, `summary`;
- `rev_no` непрерывен **в пределах одной аннотации** и считается при записи, а не
  триггером: «версия 3» в ссылке должна означать то же самое завтра;
- миграция нумерует старые строки, выводя порядок из `id`, а не из `created_at`
  (у пакетного импорта метки времени совпадают). Идемпотентна;
- **индексов на таблице не было ни одного**, хотя на неё завязаны три главных
  экрана: добавлены `idx_history_ann`, `idx_history_actor`, `idx_history_run`;
- `summary` — резюме правки в стиле Википедии, принимается API (до 200 символов),
  необязательное;
- тестом закреплён инвариант «строка в `annotations` = снимок последней ревизии».

### Акторы и прогоны агентов

- `users.kind` (`human` | `agent`) и `users.display_name` — псевдоним;
- таблица `agent_runs`: имя и версия агента, модель, путь и sha256 промпта,
  документ и параграф, статус, время. `agent_run_id` проставляется ревизии;
- `plan_agent_run_revert(run_id)` — план группового отката: для каждой затронутой
  аннотации ищется ревизия перед первой ревизией прогона; созданное самим прогоном
  помечается к мягкому удалению. Возвращается **план, а не результат**: откат
  прогона — операция на сотни строк, и её объём человек должен видеть до, а не после.

## 2026-08-21 — Ф1, часть 2: личность

**371 → 436 тестов зелёных.** Прод не трогался. Модель угрозы и обоснование
вынесены в отдельный нормативный документ `docs/anonymity-model.md`: код
ссылается на него в комментариях, и ослабить схему попутной «оптимизацией»
авторизации теперь нельзя не заметив.

### Что было

`users` хранила `email`, `name` и `picture_url` открытым текстом, доступ
выдавался таблицей `editor_allowlist` по email, а безусловные админы
перечислялись в `ADMIN_EMAILS` в окружении прода. Ежедневный бэкап БД был,
таким образом, готовым именным списком авторов.

### Что стало

- система знает про человека ровно две вещи: `sub_hash =
  HMAC(IDENTITY_PEPPER, google_sub)` и выбранный им самим псевдоним;
- из Google-токена читается **только** `sub`; email, имя и аватар не читаются
  и никуда не попадают. Проверка `email_verified` снята вместе с чтением email;
- перец живёт только в `.env.secrets`. Пустой перец — **ошибка, а не режим**:
  без него хеш вырождается в sha256 от `sub`, поэтому `hash_subject` падает, а
  вход отвечает `503`. Молчаливой деградации нет;
- доступ выдаётся одноразовыми приглашениями (`invites`), код хранится хешем и
  показывается ровно один раз; `editor_allowlist` и `ADMIN_EMAILS` упразднены,
  первый админ получает роль из `BOOTSTRAP_INVITE_CODE`;
- роль больше не пересчитывается при каждом входе: она выдаётся приглашением и
  меняется явно (`POST /api/admin/users/{id}/role`);
- появилась роль `reviewer` между `editor` и `admin`: когда основную массу
  текста производят агенты, публикация — единственное по-настоящему доверенное
  действие;
- «покинуть проект» и «отвязать участника»: `sub_hash` стирается, псевдоним
  заменяется на «Участник №N», сессии убиваются, **ревизии остаются целыми**;
- `EDITOR_TOKENS` → `AGENT_TOKENS`: вход по токену теперь честно заводит актора
  с `kind='agent'`, а не пользователя с синтетическим email `token:<имя>`;
- из выдачи API исчез `authorEmail`, джойны отдают псевдоним; логи пишут
  `actor_id` вместо email.

### Миграция прода

`scripts/api/scrub_identities.py` (dry-run по умолчанию): считает хеши из
`google_sub`, затирает `google_sub`/`email`/`name`/`picture_url`, выдаёт
псевдонимы-заглушки, чистит `editor_allowlist`. Роли сохраняются — они давно
живут в `users.role`. **Существующие участники входят после миграции без нового
приглашения**: их `sub` не меняется, меняется только способ хранения. Скрипт
идемпотентен и отказывается работать без перца.

Порядок выкладки (когда дойдёт до прода): именной бэкап `VACUUM INTO` → задать
`IDENTITY_PEPPER` в `.env.secrets` → выложить код → `scrub_identities.py`
(сначала dry-run) → убрать `ADMIN_EMAILS` из окружения → проверить вход.

### Фронтенд

Кабинет: вкладка «Allowlist редакторов» заменена на «Приглашения» (выписка,
отзыв, единоразовый показ кода), таблица пользователей показывает псевдоним,
вид актора и роль вместо email/имени/аватара; профиль — псевдоним без аватара.
На экране входа появилось поле кода приглашения; `403` отличается от сбоя входа
отдельным сообщением. `RedPenAuth.loginWithGoogle` принимает код, добавлен
`setDisplayName`.

### Тесты

(пункт из плана уборки, раздел 2.3). `test_db.py`, `test_auth.py`,

### Находка: правка через редактор не доезжает до читателя

Проверено на стенде: `POST /api/editor/...` отвечает `published: true`,
`annotations/page_014.json` обновляется — а `pages/14/index.html`, который
читает читатель, остаётся прежним. Ноль вхождений новой аннотации.

Причина: постраничный просмотрщик **не читает** `annotations/page_NNN.json`.
Он вообще ничего не загружает (инвариант офлайна), а берёт аннотации из
инлайнового `<script id="redpen-page-data">`, вшитого в HTML на сборке
(`scripts/page_html.py`). `publisher.publish_page` пишет только JSON.

То есть формула из `CLAUDE.md` — «publisher рендерит JSON → правка сразу на
сайте» — верна лишь для старого SPA, который этот JSON фетчил. Для постраничных
адресов, которые сейчас и есть сайт, она не работает. После сноса SPA (Ф6) эти
JSON-файлы не будет читать вообще никто, кроме офлайн-бандла.

**Что это значит для плана.** В Ф2–Ф3 к публикации нужно добавить шаг рендера
HTML страницы, а не только JSON: `publisher` должен звать `page_html` для
затронутой страницы (или редактор — отдельную ручку «перерисовать страницу»).
Без этого новый редактор будет писать в пустоту так же, как пишет сейчас.
Отдельно проверить, как это выглядит на проде: там страницы приезжают из
git-снапшота `redpen-publish` через content-sync, и картина может отличаться в
деталях, но механизм тот же.

Локальный обходной путь до починки — `dev/refresh-pages.sh`.

## 2026-08-21 — публикация доезжает до читателя

Тесты: 436 → **444**. Прод не трогался.

### Починка

`publisher.publish_page` теперь, кроме JSON, перерисовывает HTML страницы
читателя: новая `page_html.build_single_page(doc_dir, page_file)` рендерит одну
страницу по манифесту (соседние ссылки, заголовки, инлайновый блок), а
`publisher.render_page_html` её зовёт.

Границы, заложенные намеренно:

- **HTML не влияет на результат публикации.** Канон — JSON; страница читателя
  может отсутствовать (в `PUBLISH_DIR` нет собранного сайта — dev без тома,
  тесты). Ошибка рендера пишется в лог, но публикацию не роняет.
- **`page_html` импортируется лениво**: он тянет сборочные модули (`blog`,
  `chapters`), и API не должен от них зависеть на старте.
- **Перерисовывается только затронутая страница.** Оглавление (`index.html`) и
  `sitemap.xml` остаются артефактами сборки: они считают опубликованное по всем
  448 страницам, и делать это на каждое сохранение — не по средствам. Счётчики
  в оглавлении между сборками слегка расходятся с правдой; это известная плата.
- `publish_all()` на старте API теперь лечит и страницы, а не только JSON.

Восемь тестов в `tests/test_publish_reaches_reader.py`: правка видна читателю,
инлайновый блок совпадает с JSON, удаление убирает текст со страницы,
соседние страницы не трогаются, отсутствие манифеста не ломает публикацию.

### Следствие для процедуры деплоя контента

`content-sync` синхронизирует статику из git и исключает только
`/*/annotations/` ([content_sync.py:188](../content-sync/content_sync.py#L188)).
Каталог `/*/pages/` не исключён — значит при синхронизации страницы читателя
берутся из git-снапшота.

Само по себе это не поломка: синхронизация запускается не сама по себе, а по
webhook на push в `redpen-publish` (либо по изменению отслеживаемых клонов на
сервере), то есть в момент осознанного деплоя контента. Между деплоями страницы,
нарисованные API, живут спокойно.

Но **порядок шагов теперь важнее, чем был**. Раньше из БД в git уезжал один
производный артефакт — `annotations/*.json`; теперь их два, потому что HTML
страниц тоже производный. Правильная последовательность:

1. `export_annotations.py --to /var/redpen-data` в контейнере API — свежие JSON
   из боевой БД в рабочую копию `redpen-publish`;
2. **сборка сайта** — она перерисовывает `pages/*/index.html` из этих JSON;
3. commit + push → webhook → content-sync.

Если экспортировать и закоммитить, не пересобрав сайт, git унесёт на прод старые
страницы и затрёт ими правильные. Раньше такой ошибки быть не могло — страницы
никто, кроме сборки, не писал.

Почему API не коммитит в git сам: deploy-ключ на сервере read-only
(deployment-log, 2026-07-10), а ключ с правом записи означал бы и новую
поверхность атаки, и публичные метки времени правок в открытом репозитории —
ровно ту метаданную, которую модель анонимности минимизирует.

Страховка на случай «собрали и запушили со старым снапшотом» — кнопка
«Перепубликовать всё» в кабинете (`POST /api/admin/publish-all`): она зовёт
`publish_all()`, который теперь перерисовывает и страницы. Ничего
перезапускать не нужно.

Чтобы не было разночтений: **на обычное редактирование не перезапускается
ничего**. API пишет JSON и HTML затронутой страницы прямо в обработчике
запроса, синхронно с ответом. Перепубликация — операция раз на выкладку
контента, и то лишь если выкладку сделали не по порядку.

### Побочный эффект починки: метка обновления огрублена до дня

Перерисовка страницы на каждое сохранение сделала публичной метку
«Последнее обновление» с точностью до минуты — то есть журнал активности
редакторов прямо на сайте, без всякого гита. Часы суток выдают часовой пояс, а
при двух-трёх участниках гистограмма разделяется на людей.

Формат метки везде (`page_html`, `build_website`, `blog`) переведён на дату без
времени: читателю нужна свежесть, а минуты не дают ему ничего. Закреплено
тестом `test_reader_page_stamp_has_no_time_of_day`.

Замечание на будущее: у сайта остаются и другие временные следы — `sitemap.xml`
(`lastmod`) и заголовки веб-сервера. Их стоит проверить отдельно, когда дойдут
руки до выкладки.

## 2026-08-21 — ?only= и кнопка «Открыть» в кабинете

`?only=<annId>` в постраничном просмотрщике: скан с единственным выделенным
маркером и панель из одного комментария. Это по-прежнему фильтрация уже
встроенных данных — ни одного запроса, инвариант офлайна цел. Черновик по такой
ссылке показывается без `?tags=draft`: ссылка адресная, а не обзорная.

Кнопка «Открыть» в кабинете вела на `<doc>/?p=<label>&editor=1&ann=<id>` — то
есть на оглавление, где редакторских скриптов нет; она не работала (описано в
`editor-app-design-brief.md` §2). Теперь ведёт на
`<doc>/pages/<label>/?only=<id>`. Это просмотр, а не правка: режим
редактирования живёт только в старом SPA и переезжает в отдельное приложение —
честнее вести на рабочий просмотр, чем на сломанную правку. Когда появится
`/app/`, ссылка переедет туда.

## 2026-08-21 — ночной снапшот БД → git

`scripts/nightly_snapshot.py` — раз в сутки выгружает аннотации из БД в клон
`redpen-publish`, перерисовывает страницы и оглавление, коммитит и пушит, если

Почему раз в сутки, а не на каждую правку: коммит на каждое сохранение — это
публичная хронология работы редакторов с точностью до минуты. Суточная пачка
огрубляет её до дня, как и всё остальное в `anonymity-model.md`. Автор коммита —
`redpen-bot`, людей в истории публичного репозитория нет.

### Чтобы коммиты были читаемыми

Две вещи пришлось поправить, иначе ночной диф был бы бесполезен:

- **Метка обновления не перезаписывается зря.** `page_html` теперь сравнивает
  новую страницу со старой, игнорируя строку «Последнее обновление», и не трогает
  файл, если изменилась только она. Без этого каждая пересборка меняла все 448
  файлов разом. Заодно метка стала честной: у страницы, чьи аннотации никто не
  трогал полгода, она показывает ту давнюю дату, а не день последней сборки.
- **JSON пишется байт в байт** как у живого публикатора и `export_annotations.py`
  (`indent=2`, без завершающего перевода строки), иначе файлы дёргались бы
  туда-обратно в зависимости от того, кто писал последним.

Проверено на данных стенда: повторный прогон без правок — «изменений нет»;
одна правка через API — коммит ровно из трёх файлов (JSON страницы, сама
страница, оглавление со счётчиком).

### Режимы

- по умолчанию — отчёт, ничего не пишет;
- `--apply` — записать файлы и закоммитить;
- `--push` — плюс `git push`;
- `--write-only` — только записать файлы, git не звать. Для запуска **внутри
  контейнера API**, где git может быть не установлен, а ключ с правом записи
  держать не хочется: коммит и push делаются снаружи, в том же клоне.

### Что мешает поставить на прод

1. **Deploy-ключ на сервере read-only** (deployment-log, 2026-07-10). Пуш без
   ключа с правом записи невозможен. Ключ с правом записи в контейнере, который
   смотрит в интернет, — новая поверхность атаки; отсюда и `--write-only`:
   ключ остаётся на хосте, контейнер только пишет файлы.
2. **Бинд-маунт `./redpen-publish` на сервере — директория-заглушка**, а не клон
   репозитория (deployment-log, 2026-07-09). Пока там нет настоящего клона,
   писать снапшоту некуда.

Пока это не решено, ночной прогон ставить нельзя, а процедура выкладки контента
остаётся ручной и требует порядка «экспорт → сборка → коммит».

### Почему прогон разделён на две половины

На проде **ни один процесс не видит одновременно и базу, и git-клон**:

| | база (`redpen_db`) | живой клон (`data/redpen-content`) |
|---|---|---|
| контейнер API (uid 10001) | да, `/var/redpen-db` | нет |
| хост (root) | только через путь тома | да, но `root:root` |
| content-sync | нет | да, `/srv/repo` |

Свести их в одном процессе можно тремя способами, и два плохи:

- **дать API бинд-маунт клона** — клон `root:root`, значит нужен `chown` на
  uid 10001, после чего root-процессы снова создадут там свои файлы (это ровно
  те грабли, что описаны в памяти `redpen-storage-permissions-gotcha`). Плюс
  коммит и push пришлось бы делать изнутри контейнера, то есть положить туда
  ключ с правом записи — в контейнер, смотрящий в интернет;
- **всё на хосте** — тогда root открывает боевую SQLite и создаёт `-wal`/`-shm`
  от своего имени, а API под uid 10001 теряет к ним доступ. Те же грабли;
- **разделить** ← выбрано. Контейнер выгружает JSON туда, куда уже имеет право
  писать (`/var/redpen-data`, владелец 10001, на хосте это
  `infra/redpen-publish`). Хост забирает файлы оттуда и коммитит в клон своим
  ключом. Ни новых монтирований, ни смены владельца, ни ключа в контейнере.

Под это в скрипт добавлены `--from <каталог>` (брать готовые JSON вместо БД; в
этом режиме база **не открывается вовсе**) и `--no-pages`. Импорты модулей
проекта сделаны ленивыми: хостовой половине не нужен ни один файл проекта, кроме
самого скрипта — есть тест, запускающий его вне репозитория с пустым окружением.

### Порядок постановки

**Шаг 1 — только JSON, работает на сегодняшнем коде прода.** Ровно то, что было
заказано («json → git»), и ничего сверх: страницы не трогаются, выкладки нового
кода не требуется. `export_annotations.py` в контейнере уже есть, в боевой БД
1275 аннотаций на 315 страницах.

```
0 0 * * * docker exec redpen-api-1 python /app/scripts/api/export_annotations.py --to /var/redpen-data \
  && /usr/bin/python3 /root/apps/redpen/infra/scripts/nightly_snapshot.py \
       --repo /root/apps/redpen/data/redpen-content \
       --from /root/apps/redpen/infra/redpen-publish \
       --no-pages --push
```

На хост нужно положить один файл — `scripts/nightly_snapshot.py`.

**Шаг 2 — плюс страницы, только вместе с выкладкой нового кода.** Убрать
`--no-pages`. Раньше нельзя: рендер новым `page_html` выложил бы заодно
категории и прочие невыложенные изменения, а это отдельное решение (Ф0).
