# Редактор как отдельное приложение — вводные к проектированию

Составлено 2026-08-21. Это **не план**, а собранная фактура для следующей
итерации планирования: что редактор делает сегодня, на чём держится, что
переиспользуется, что отмирает и какие решения нужно принять до кода.
Решение о направлении принято пользователем: редактор работает с базой через
API и не должен подчиняться ограничениям просмотрщика.

Контекст и порядок работ — `docs/refactoring-plan-2026-08.md` (раздел 5).

---

## 1. Почему переезд вообще нужен

Просмотрщик и редактор склеены одним DOM, и требования у них
противоположные:

| | просмотрщик | редактор |
|---|---|---|
| сеть | ноль запросов, инвариант офлайна | API, авторизация, CSRF |
| состояние | нет | черновик, baseline, «грязная» форма, блокировка версий |
| аудитория | все | 2–3 человека с ролью `editor`/`admin` |
| доставка | статика на любом носителе | обычное веб-приложение |

Пока они в одном файле, каждое улучшение редактора упирается в инвариант
статики, а каждая правка просмотрщика рискует задеть редактор.

## 2. Где редактор живёт сегодня (факты, проверено на проде)

- Точка входа — **только** `<doc>/document_index.html?p=<метка>&editor=1`.
  Файл `<doc>/index.html` на шаге 3.6 сборки перезаписывается оглавлением,
  поэтому SPA выживает лишь во второй копии.
- Кабинет строит ссылку как `../<docId>/?p=<label>&editor=1&ann=<id>`
  ([cabinet.js:149](../templates/cabinet/cabinet.js#L149)) — то есть **на
  оглавление**, где редакторских скриптов нет. Переход из кабинета в редактор
  сегодня, судя по всему, не работает; проверить руками и не чинить костылём —
  правильная починка это и есть переезд.
- Постраничный просмотрщик редактор не поддерживает вовсе.

## 3. Инвентарь: что переиспользуется, что отмирает

| Файл | Строк | Судьба |
|---|---|---|
| [redpen-auth.js](../templates/js/redpen-auth.js) | 161 | **Переиспользовать как есть.** Общий с кабинетом: `apiBase`, `getCsrf`, `me`, `loginWithToken`, `loginWithGoogle`, `logout`, `loadGis`, `renderGoogleButton`. |
| [redpen-editor-panel.js](../templates/js/redpen-editor-panel.js) | 282 | **Переиспользовать почти как есть.** Автономна: `mount(container)`, `setDraft`/`getDraft`, `validate`, `setAuthState`. Зависит только от собственного DOM. |
| [redpen-editor-bootstrap.js](../templates/js/redpen-editor-bootstrap.js) | 1173 | **Разобрать.** Ниже разбивка. |
| [cabinet/](../templates/cabinet/) | 654+255+html | **Образец архитектуры.** Уже устроен так, как должен быть устроен редактор: своя точка входа, свой html/js/css, весь контент из API, авторизация через `RedPenAuth`. |

Что внутри бутстрапа стоит сохранить:
- **пересчёт координат** «клик по картинке → координаты оригинала»
  (`clientToOriginal`, [:228](../templates/js/redpen-editor-bootstrap.js#L228)) —
  ядро редактирования, переносится целиком;
- **оптимистическая блокировка**: хранение `serverPageSha`, обработка `409`
  и предложение перечитать страницу;
- **`annIdFromDom()`** ([:34](../templates/js/redpen-editor-bootstrap.js#L34)) —
  нормализация id, лечение бага №2 (префикс `circle-` уезжал в API);
  в новом коде id вообще не должен ходить через DOM, но правило сохранить;
- **защита от потери изменений** (`isDirty`/`confirmLoseChanges`,
  [:111](../templates/js/redpen-editor-bootstrap.js#L111)) — поведение, к
  которому пользователь привык;
- **обработка ошибок API**: 401 → показать вход, 403 viewer → «недостаточно
  прав», 403 CSRF → тихий ретрай с новым токеном, 409 → конфликт версий.

Что отмирает вместе с SPA:
- внедрение панели в чужой DOM (`#global-comment-container`,
  `#image-container`) и вся зависимость от разметки просмотрщика;
- **весь легаси типа `general`** — 29 упоминаний в файле: отложенная
  подстановка, кэш общих комментариев, `findGeneralOnPage`,
  `initGeneralCache`. Тип упразднён миграцией 2026-08-16;
- дублирующая реализация авторизации: бутстрап содержит **собственные**
  `apiBase`/`withJsonHeaders`/`loadGoogleIdentityServices`/`renderGoogleButton`
  ([:258](../templates/js/redpen-editor-bootstrap.js#L258),
  [:382](../templates/js/redpen-editor-bootstrap.js#L382)) параллельно
  `redpen-auth.js` — в новом приложении остаётся один `RedPenAuth`;
- третья копия карты размеров маркера
  ([:903](../templates/js/redpen-editor-bootstrap.js#L903));
- легаси-эндпоинт `GET /api/pages/{pageId}`
  ([:491](../templates/js/redpen-editor-bootstrap.js#L491)) — в новом коде
  только `/api/editor/...`.

## 4. Что API уже умеет (менять, скорее всего, не придётся)

- `GET /api/editor/{docId}/{pageNum}` → `{pageId, serverPageSha, annotations}`;
  для сессии `editor`/`admin` включает черновики с `draft: true`.
- `POST /api/editor/{docId}/{pageNum}` — создать/обновить;
  `PUT /api/editor/{docId}/{pageNum}/{annId}` — обновить по id;
  `DELETE .../{annId}` — мягкое удаление. Тело:
  `{annType, text, coords?[x,y], id?, clientPageSha?, status?, tags?}`.
  Отсутствие `tags` = «не трогать», `[]` = «очистить».
- `GET /api/annotations`, `GET /api/history`, `GET /api/tags`,
  `POST /api/history/{histId}/revert`, `GET /api/stats` — всё, на чём уже
  работает кабинет.
- Авторизация: сессионная кука + CSRF, роли `viewer`/`editor`/`admin`,
  Google Sign-In или личный токен.

Единственное, чего в API нет для полноценного редактора, — **картинка
страницы**; она берётся статикой (`<doc>/images/<page_file>.png`), и это
нормально: редактору статика доступна так же, как читателю.

## 5. Вопросы, на которые нужен ответ до проектирования

1. **Границы приложения.** `/editor/` рядом с `/cabinet/` — или кабинет и
   редактор это одно приложение с двумя экранами? Сейчас они делят авторизацию,
   таблицу аннотаций, фильтр по тегам и понятие «страница»; расхождение
   стоило нам сломанной ссылки между ними.
2. **Экран.** Одна страница книги за раз (как сейчас) или список слева +
   рабочая область справа (как в кабинете)? От этого зависит адресация:
   `/editor/?doc=&page=&ann=` против внутренней навигации.
3. **Предпросмотр.** Нужен ли редактору вид «как на сайте»? Если да — это
   единственная причина переиспользовать `page-view.js` (или его часть);
   если нет — редактор рисует маркеры сам, проще и без связи с просмотрщиком.
4. **Теги.** UI редактирования тегов не сделан до сих пор (API готов,
   `GET /api/tags` есть, PUT без `tags` их сохраняет). Делать сразу в новом
   редакторе — или отдельной задачей?
5. **Рабочий процесс с черновиками.** На проде 1007 черновиков от
   агента-аннотатора. Редактор сегодня — «правка одной аннотации»; нужен ли
   режим приёмки потоком (следующий черновик → принять/поправить/отклонить)?
   Это меняет весь дизайн экрана. Смежное: в `db.py` до 2026-08-21 лежала
   неподключённая ревью-подсистема (вердикты `excellent`/`ok`/`bad`, кворум из
   двух рецензентов, `review_coverage`) — удалена как мёртвая, но
   восстанавливается из git, если модель приёмки окажется нужна.
6. **Мобильный редактор** — нужен ли вообще? Сейчас поддержка мобильного
   режима есть у просмотрщика, а у редактора фактически нет.
7. **Судьба `?editor=1`.** После переезда параметр и ветка в
   [legacy-page-redirect.js:17](../templates/js/legacy-page-redirect.js#L17)
   удаляются. Нужен ли редирект со старых редакторских ссылок на новый адрес?

## 6. Ограничения, которые нельзя нарушить

- **Просмотрщик остаётся полностью статическим.** Ни один файл, который
  отдаётся читателю, не должен получить сетевую зависимость. Проверка простая:
  в `pages/*/index.html` и `page-view.js` не появляется ни `fetch`, ни
  абсолютных адресов (запрет зафиксирован в шапке
  [page-view.js:9](../templates/js/page-view.js#L9)).
- **Порядок работ:** новый редактор → приёмка → снос SPA. Не наоборот.
- Прод трогать только с явного подтверждения; перед миграциями данных —
  именной бэкап БД (`VACUUM INTO`).
- `compute_page_sha` не расширять — это вход оптимистической блокировки.
