# Спецификация формата замечаний

## Общая структура
Файл состоит из одного или нескольких замечаний. Каждое замечание представляет собой YAML-документ с frontmatter и телом замечания.

## Разделители
- Каждое замечание начинается с `~~~meta` на отдельной строке
- После frontmatter следует `~~~` на отдельной строке
- Между замечаниями должна быть как минимум одна пустая строка для лучшей читаемости

## Frontmatter
Обязательные поля:
- `kind`: вид замечания (см. раздел «Виды замечаний»)
- `id`: уникальный идентификатор замечания (теперь обязателен для всех замечаний)

Необязательные поля:
- `target`: идентификатор цели, к которой относится замечание. Если значение имеет формат `[X, Y]`, где `X` и `Y` — числовые значения, то это интерпретируется как координаты точки на изображении страницы
- `tags`: список тегов в квадратных скобках, `tags: [omission, framing, tc-usa-origin]`
  (см. раздел «Теги»)
- `confidence`: `high` / `medium` / `low` — конвертер превращает его в тег
  `confidence:<значение>`

## Виды замечаний
В системе используются два вида замечаний:
- `major` — крупное замечание к тексту или области (крупный маркер на скане);
- `minor` — обычное замечание (маркер меньшего размера).

Вид задаёт **только размер маркера и порядок в панели**. Цвет идёт от категории
приёма (`docs/annotation-classification-2026-08.md`), а не от вида.

У обоих `target` обязателен. Существовавший ранее вид `general` («общее замечание
к странице», без привязки) упразднён: он не оправдал себя в интерфейсе, а с переходом
на постраничные адреса каждому замечанию нужен якорь на скане. Конвертер отвергает
`general` с ошибкой. История миграции 16 таких замечаний —
`docs/general-migration-map.json`.

### Прежние имена (до 2026-08-29)

До переименования сущности ключ назывался `type`, а значения — `main` и
`comment`. Конвертер читает и их (`main` → `major`, `comment` → `minor`), но
пишет только текущие. Черновики в `redpen-content` переведены разом скриптом
`scripts/ops/rename_meta_type_to_kind.py`.

## Тело замечания
- Следует сразу после `~~~`
- Может содержать любой валидный markdown
- Может быть многострочным
- Не должно содержать линий, начинающихся с `~~~meta` или `~~~` (это зарезервировано для разделителей)

## Примеры

### Пример 1: Замечание с target
```
~~~meta
kind: major
id: ann-page7-1
target: page_007_line003
~~~

Это не вопрос, это утверждение в форме вопроса. Тебе пытаются сразу навязать идею о том, что СССР быстро восстановил хозяйство и экономику.
```

### Пример 2: Замечание с координатами
```
~~~meta
kind: minor
id: ann-page8-2
target: [450, 320]
~~~

Начало работы по восстановлению представлено как само собой разумеющееся «колоссальных усилий», но нет ни слова о жертвах.
```

### Пример 3: Замечание с идентификатором цели
```
~~~meta
kind: major
id: ann-page10-1
target: page_010_block1
~~~

Крупное замечание к блоку текста на странице.
```

### Пример 4: Замечание ко всей странице
Отдельного вида для этого нет — привяжи его к месту, где приём виден отчётливее
всего (заголовок раздела, вопрос параграфа, открывающая иллюстрация):
```
~~~meta
kind: major
id: ann-page10-3
target: [450, 275]
~~~

Приём, который проходит через весь параграф: …
```

## Правила валидации
1. Каждый документ должен начинаться с `~~~meta`.
2. Обязательны поля `kind` и `id`. Поле `target` является необязательным.
3. Если поле `id` присутствует, оно должно быть уникальным в пределах всех замечаний.
4. После метаданных должен быть разделитель `~~~`.
5. Между замечаниями должна быть пустая строка.
6. Содержимое замечания не должно начинаться с `~~~meta` или `~~~`.
7. Вид замечания должен быть одним из перечисленных в разделе «Виды замечаний».
8. Если поле `target` имеет формат `[X, Y]`, где `X` и `Y` — числовые значения, то это интерпретируется как координаты.

## Рекомендации по именованию
- `id`: формат `ann-pageN-М`, где `N` — номер страницы, `М` — порядковый номер замечания на странице.

## Обработка
При парсинге:
1. Разбить файл по `~~~meta` и `~~~` с учётом пустых строк.
2. Для каждого замечания:
   - Извлечь и валидировать метаданные.
   - Остальной текст считать телом замечания.
3. Проверить уникальность поля `id`.
4. Если поле `target` имеет формат `[X, Y]`, где `X` и `Y` — числовые значения, то это интерпретируется как координаты и преобразуется в список целых чисел для поля `coords` в JSON.

## Формат JSON

При конвертации в JSON формат, поля из markdown преобразуются следующим образом:
- `kind` -> `kind` (в md ключ тот же; прежний `type` читается)
- `target` -> `targetBlock` (если `target` не содержит координаты)
- `target` -> `coords` (если `target` имеет формат `[X, Y]`, преобразуется в массив чисел)
- `id` -> `id`
- Текст замечания -> `text`
- `tags` + `confidence` -> `tags` (массив строк; `confidence: high` становится
  элементом `confidence:high`)

Пример JSON:
```json
[
  {
    "id": "ann-page8-1",
    "text": "Автор использует термин «самая кровопролитная война» без источника и без указания методики оценки.",
    "kind": "major",
    "coords": [
      350,
      220
    ]
  },
  {
    "id": "ann-page8-2",
    "text": "Начало работы по восстановлению представлено как само собой разумеющееся «колоссальных усилий».",
    "kind": "minor",
    "coords": [
      450,
      320
    ]
  }
]
```

## Теги

Тег — строка из латиницы, цифр, `-` и `:` (`omission`, `tc-usa-origin`,
`confidence:high`), до 64 символов, до 32 тегов на замечание. Регистр
приводится к нижнему, дубликаты отбрасываются. Соглашение `prefix:value`
(`confidence:high`) заменяет отдельные поля — новые «измерения» не требуют
колонок в БД.

Хранение — таблица `remark_tags` (боковая, а не колонка: апсерт замечания
перечисляет все изменяемые колонки, и любой вызывающий, не знающий про теги,
затирал бы их). Отсутствие ключа `tags` в запросе означает «не трогать», явный
`[]` — «очистить».

**Зарезервированы имена `draft`, `published`, `deleted`.** Записать их нельзя
(400 от API, `db.TagError` в скриптах): статус живёт в колонке `status`, а тег
`draft` — производный, его подставляет публикатор при рендере. Дуального
источника правды нет.

Реестр типовых приёмов (`tc-*`) — `redpen-content/<docId>/remarks_draft/_typical_remarks.md`.

## Действия и их типы

Журнал `remark_history` отвечает на два разных вопроса, и до 2026-08-30 отвечал
только на первый.

- **`action`** — как была сделана запись: `create`, `update`, `delete`,
  `revert`, `import`, `backfill`. Это происхождение ревизии, её инструмент.
- **`changes`** — что при этом изменилось: JSON-массив токенов из словаря
  `scripts/api/remark_actions.py`. Считается на записи диффом со снимком
  предыдущей ревизии.

Разделять их пришлось потому, что одно сохранение через `PUT /api/editor/...`
записывалось как `update` независимо от того, поправили ли текст, опубликовали
ли черновик или сменили категорию, — и отфильтровать «покажи только правки
текста» было нельзя.

| токен | что означает |
|---|---|
| `create` | первая ревизия замечания |
| `text` | изменён текст |
| `coords` | передвинут маркер на скане |
| `kind` | `major` ⇄ `minor` |
| `publish` | `draft` → `published` |
| `unpublish` | `published` → `draft` |
| `delete` | переход в `deleted` |
| `restore` | возврат из `deleted` |
| `category` | сменена категория |
| `tags` | изменён набор тегов |
| `revert` | ревизия получена откатом |
| `rate` | проставлена оценка (не ревизия, см. ниже) |
| `note` | оставлен комментарий (не ревизия, см. ниже) |

Правила, на которых легко ошибиться:

- **токенов может быть несколько**: сохранение, поменявшее текст и категорию,
  даёт `["text", "category"]`. Модель это выдерживает, а расширение словаря
  `action` — не выдержало бы;
- **направление перехода статуса зашито в токен** (`publish` против
  `unpublish`): на записи известны оба состояния, на чтении за прошлым пришлось
  бы ходить отдельным запросом;
- **пустой массив — законный результат**: сохранение, ничего не изменившее,
  честно не содержит действий;
- **`NULL` означает «не вычислено»**, а не «ничего не изменилось». Так помечены
  ревизии, записанные до появления колонки; заполняет их
  `scripts/api/backfill_history_changes.py` (по умолчанию отчёт, запись по
  `--apply`). Фильтр по составу такие строки не показывает: догадка в журнале
  аудита хуже пропуска;
- **ярлык для человека считает сервер** и отдаёт готовым в поле `actionLabel`.
  JS-двойник словаря пришлось бы держать синхронным руками — эта цена уже
  платится за категории (`annotation_categories.py` ↔ `redpen-categories.js`),
  второй раз её платить незачем.

Фильтр: `GET /api/history?changed=<токен>` — по составу изменения;
`?action=<значение>` — по происхождению записи. Это разные вопросы.

Узкие операции, каждая из которых даёт ровно один токен:

| маршрут | тело |
|---|---|
| `PATCH /api/editor/{docId}/{pageNum}/{remarkId}/status` | `{status, summary?}` |
| `PATCH /api/editor/{docId}/{pageNum}/{remarkId}/category` | `{category\|null, summary?}` |
| `PATCH /api/editor/{docId}/{pageNum}/{remarkId}/tags` | `{tags: [...], summary?}` |

`serverPageSha` они не требуют: оптимистическая блокировка защищает текст и
координаты, где двое правят одно и то же. Публикация черновика при этом sha
страницы всё же сдвигает — черновики не входят в `render_page()` — и открытая
сессия редактора получит 409 на следующем сохранении. Это правильно: страница
действительно стала другой.

## Оценки и комментарии — данные редактора

Ни то, ни другое **не попадает в статику**: ни в `remarks/page_NNN.json`, ни в
инлайновый блок `redpen-page-data`. Это не «пока не сделано», а условие задачи
(главный инвариант проекта, `docs/README.md`).

Ни то, ни другое **не является ревизией**: строка в `remarks` от них не
меняется, а `rev_no` обязан остаться citable номером версии — «версия 3» должна
завтра означать то же самое, а не сдвинуться от того, что кто-то поставил
оценку. Поэтому у обоих свои таблицы, а сводятся они только на чтении, в
`GET /api/remarks/{docId}/{pageKey}/{remarkId}/timeline`.

**Оценки** (`remark_ratings`) — три шкалы вместо одного вердикта:
`interest` (интересность факта), `importance` (важность),
`admissibility` (допустимость), каждая 1–5, растёт в сторону названного
качества. Шкалы заданы в `scripts/api/rating_scales.py`; добавление шкалы —
правка словаря, без миграции. Одна оценка на (замечание, шкала, участник),
повторная перезаписывает прежнюю — **журнала изменения оценок нет**. Оценка
ничего не публикует и ничего не скрывает: кворум из удалённой ревью-подсистемы
не воскрешён, публикация остаётся явным действием редактора.

**Комментарии** (`remark_notes`) — рабочее обсуждение замечания. Тред ровно в
один уровень: ответить можно только на корневой комментарий. «Решено» ставится
на корень и снимается им же; закрыть тред может любой редактор (решение — про
работу, а не про авторство), править текст — только автор. Удаление мягкое:
строка остаётся ради связности треда, тело затирается.

## Черновики и фильтрация по URL

У замечания в БД есть статус (`published` / `draft` / `deleted`). Публикатор
(`scripts/api/publisher.py`, `render_page_static`) рендерит в
`remarks/page_<NNN>.json` **и опубликованные, и черновики одним массивом**;
у черновика в элементе стоит `"draft": true` и тег `draft` первым в `tags`:

```json
[
  {"id": "ann-p008-1", "text": "…", "kind": "major", "coords": [350, 220],
   "tags": ["omission", "confidence:high"]},
  {"id": "ann-p008-2", "text": "…", "kind": "minor", "coords": [450, 320],
   "draft": true, "tags": ["draft", "framing"]}
]
```

Отдельного файла `page_<NNN>.drafts.json` больше нет.

Каталог называется `remarks/`. Прежнее имя `annotations/` publisher **пока
дублирует байт в байт** — ради уже розданных офлайн-копий и старых адресов;
дублирование снимается вместе с 301-редиректом (фаза 6 переименования).

Просмотрщик (`templates/js/main.js`, `getTagFilter()`) фильтрует массив по
URL-параметрам (работают и в query, и в hash):

- `?only=<id>` — показать ровно одно замечание: скан с единственным
  выделенным маркером. Постоянная ссылка на замечание; черновик по ней виден
  без `?tags=draft`, потому что ссылка адресная, а не обзорная. Остальные
  фильтры при этом не применяются;
- `?tags=a,b` — оставить замечания, у которых есть хотя бы один из тегов;
- `?notags=a,b` — скрыть замечания с любым из тегов;
- исключение всегда сильнее включения;
- **черновики скрыты по умолчанию**: если `draft` не упомянут ни в одном из
  списков и нет `?showDrafts=1`, он добавляется в исключения.

`?showDrafts=1` сохранён как легаси-написание `?tags=draft`. Черновики рисуются
пунктирным кружком и помечаются `[черновик]` в попапе и в общем блоке. Режим
редактора (`?editor=1`) фильтр отключает: редактор тянет свои живые черновики
напрямую из API и рисует их сам.

Инвариант статики сохранён: просмотрщик по-прежнему не обращается к API. Учтите,
что файл **публично доступен** по прямой ссылке; «скрытость» черновиков держится
только на незнании URL и переменной (так же, как раньше — файл-компаньон тоже
раздавался публично).

**Важно для API:** в ответе `GET /api/editor/{docId}/{pageNum}` черновик помечен
только булевым `draft: true`, тег `draft` в `tags` не кладётся. Редактор
возвращает полученные поля в PUT, а `draft` — зарезервированное имя, которое
вернулось бы как 400. Зеркалирование статуса в тег — только в статическом рендере.

`compute_page_sha` считается по `render_page()` — «голому» формату без тегов и
без черновиков. Это вход оптимистической блокировки редактора; правка тегов
или черновика его не двигает (и, соответственно, под блокировкой не находится).
