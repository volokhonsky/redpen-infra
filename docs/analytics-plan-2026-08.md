# Аналитика без счётчиков: что можно узнать из серверных логов

Составлено 2026-08-23, переработано в тот же день после решения ставить
готовый инструмент. Описывает, что мы можем измерять, чего не можем
принципиально, и как это устроено. Дашборды считает **Matomo** (импорт
серверных логов — его штатная функция); свой код остался только там, где
готовый инструмент про наш контент знать не может. Написано и покрыто тестами,
**на прод не выложено** — см. «Как выкладывать».

## Почему вариант ровно один

Любой внешний счётчик — Google Analytics, Яндекс.Метрика, Plausible, Umami,
GoatCounter — работает так: страница читателя обращается к чужому серверу.
Неважно, JS это или «безджаваскриптовый» пиксель `<img>`: обращение всё равно
есть. Это ломает **главный инвариант проекта** (просмотрщик не ходит в сеть,
сайт работает с флешки — `docs/README.md`) и вдобавок отдаёт третьей стороне
список читателей сайта про школьный учебник, за чтение которого в стране
издания могут спросить.

Поэтому единственная допустимая аналитика — **серверная, постфактум, по логам,
которые и так пишутся**. Ноль байт на стороне читателя, ноль кук, ноль запросов.

## Сессий у читателя нет — и это не оплошность

- Просмотрщик не ставит **ни одной куки** и не хранит ничего в `localStorage`.
- Просмотрщик не делает **ни одного запроса к API** — только статика по
  относительным путям.
- Сессия (`redpen_session`) существует только у редактора и кабинета — это
  считанные люди из закрытого круга, к аудитории отношения не имеет.

Значит, «визит» — не факт, а гипотеза, которую мы восстанавливаем из логов.
Насколько точно — см. «Сессионизация».

## Что уже пишется на проде (без единой правки)

| источник | что содержит | IP читателя |
|---|---|---|
| `docker logs frontend` (nginx, формат `combined`) | путь, статус, размер, `Referer`, `User-Agent`, время | **нет** — виден только адрес контейнера Caddy |
| `/data/caddy.log` (Caddy, `info`) | ошибки, TLS-рукопожатия; с 2026-08-23 5 МБ × 2, 168 ч | да, в строках ошибок |
| `docker logs api` (uvicorn) | обращения к API | адрес контейнера Caddy |
| `redpen.db` | аннотации, ревизии, `agent_runs`, `sections` | — |

Ключевой факт: **nginx уже пишет полную картину трафика читателя и при этом не
знает, кто пришёл.** Это готовый, уже анонимный источник, и в нём накоплена
история за всё время жизни контейнера.

Проверить на проде перед началом работ (ретроспектива может быть обрезана
ротацией демона docker):

```bash
docker inspect -f '{{.LogPath}}' redpen-frontend-1 | xargs ls -lh
docker logs redpen-frontend-1 2>/dev/null | head -1
```

Отдельно: access-лог **самого Caddy сейчас выключен** — в `caddy/Caddyfile`
директива `log` стоит только в глобальном блоке, а доступ логируется лишь при
`log` внутри блока сайта. То есть адреса посетителей систематически на диск не
попадают. Это хорошее состояние по умолчанию, и менять его надо осознанно.

## Что измеримо

### Спрос на контент
1. **Просмотры по страницам** — путь `/<docId>/pages/<label>/` даёт книгу и
   страницу без всякой догадки.
2. **Просмотры по параграфам и главам** — свернуть страницы через таблицу
   `sections` (`page_start`/`page_end`). Параграф — наша единица работы, значит
   и единица отчёта.
3. **Спрос против покрытия** — соединить просмотры с числом аннотаций на
   странице из БД. Ответ на вопрос «какой параграф разбирать следующим» перестаёт
   быть вкусовым: видно, какие неразобранные страницы читатель уже открывает.
4. **`?only=<annId>`** — постоянная ссылка на один комментарий. Каждое такое
   попадание означает, что комментарий кому-то **переслали**. Это единственная
   прямая обратная связь по качеству отдельных аннотаций, которая у нас вообще
   есть.
5. **Легаси-адреса** `?page=N` и `?p=` — сколько ссылок старого формата ещё
   ходит по сети.
6. **Вторая книга** (10 класс, `noindex`, без аннотаций) — находит ли её кто-то.
7. **Скачивания офлайн-архива** — когда он появится на проде.

### Поведение
8. **Динамика** — по часам, дням, дням недели. Всплески после публикаций и
   после чужих упоминаний.
9. **Источники** — `Referer`: поисковики, `t.me`, соцсети, прямые заходы.
   Поисковики сам запрос не отдают — только факт, что пришли от них.
10. **Глубина чтения** — сколько страниц за визит, подряд ли (`page N → N+1`)
    или прыжками, доходят ли до конца параграфа. Требует сессионизации.
11. **Точки входа и выхода**, доля визитов из одной страницы.
12. **Человек или робот** — надёжный признак без JS: живой браузер после HTML
    тянет тяжёлый скан `images/page_NNN.png`, css и js; краулер обычно берёт
    только HTML. Соотношение «HTML без картинки» отсекает ботов лучше, чем
    список `User-Agent`.

### Здоровье системы
13. **404** — битые ссылки, в том числе чужие, и недоехавшая публикация.
14. **5xx и время ответа**, доля `304` (кэш работает), объём отданного трафика.
15. **Обходы поисковиков** — Googlebot/YandexBot по книгам, `sitemap.xml`,
    `robots.txt`: видно, идёт индексация или нет.
16. **Срабатывания вебхука** `/.hooks/redpen-publish` — фактический журнал
    выкладок контента.

### Из БД, без всяких логов
17. Покрытие книг аннотациями по параграфам, черновики против опубликованных,
    распределение по семи категориям и по тегам, история прогонов агента,
    ревизии по неделям. Данные уже есть — нужен только отчёт.

## Чего не будет никогда (при этом подходе)

- **Время на странице.** Нет события ухода. Matomo оценит его по интервалу
  между запросами внутри визита, но последняя страница визита не измеряется
  вовсе — это свойство любой аналитики по логам.
- **Клики по кружкам, раскрытие комментариев, прокрутка.** Это целиком клиент,
  запросов не порождает. То есть **мы не узнаем, читают ли комментарии** —
  только что страницу открыли. Единственное исключение — `?only=`.
- **Точная география и устройство.** Matomo и то и другое покажет, но по
  `User-Agent` и адресу, то есть с обычной для логов погрешностью.
- **Читатели офлайн-архива** — не видны вообще. Это свойство, а не потеря.

Уникальные посетители и возвраты между днями при этом **есть**: их считает
Matomo своей штатной схемой опознания. Своей второй схемы мы не заводим — см.
`docs/anonymity-model.md`, раздел «Читатели сайта».

## Разделение труда

Первая версия этого документа предлагала считать всё самостоятельно. Это была
ошибка соразмерности: посещаемость по дням, источники, устройства, страны,
точки входа и глубина визита — решённая задача, и решать её заново незачем.

| | кто считает |
|---|---|
| посещаемость, визиты, источники, устройства, страны, точки входа | **Matomo** |
| просмотры в свёртке **по параграфам** | Matomo (см. приём с адресом) |
| **спрос против покрытия** — читают, а разбора нет | наш код (нужна каноническая БД) |
| открытия по `?only=` — какие комментарии пересылают | наш код |
| выброс следов редактора и кабинета из аналитики | наш код, на подготовке лога |

### Приём, дающий «по разделам»

Matomo строит отчёт по адресам страниц иерархически, по сегментам пути. Про
наши параграфы он ничего не знает, но если параграф **сделать сегментом
адреса** при подготовке лога, посещаемость по разделам получается сама:

```
/medinsky11klass/pages/210/   →   /medinsky11klass/§19/210/
```

В отчёте это разворачивается в «книга → § 19 → страница 210». Цена приёма:
адрес в отчёте не настоящий, и переход по строке отчёта ведёт в никуда.
Настоящий адрес — `/<doc>/pages/<label>/`; при необходимости приём отключается
(`--no-sections`), а вид сегмента меняется (`--section-prefix`).

## Что сделано

- `scripts/analytics.py` — чистая библиотека: разбор JSON-лога Caddy,
  классификация путей, преобразование в `ncsa_extended`, подстановка параграфа
  в адрес.
- `scripts/page_sections.py` — границы параграфов по манифесту книги; общий
  модуль для экспорта и счётчиков.
- `scripts/matomo_export.py` — готовит лог для `import_logs.py`: Caddy пишет
  JSON, Matomo из коробки читает `ncsa_extended`. Здесь же выбрасываются
  запросы редактора и кабинета и подставляется параграф. Позиция в логе
  двигается **только после успешного импорта** (`--commit`): `import_logs.py`
  не возобновляемый, и упавший импорт иначе унёс бы строки навсегда.
- `scripts/ops/redpen_stats.py` — счётчики контента: параграфы, спрос против
  покрытия, `?only=`, легаси-адреса, скачивания архива. Ни адреса, ни
  производной от него не хранит.
- `scripts/ops/redpen-stats` — крон: счётчики, экспорт, импорт, коммит позиции;
  раз в сутки чистка старых записей.
- `tests/test_analytics.py` — 51 тест. Главные не про арифметику: запросы
  редактора и кабинета не попадают ни в Matomo, ни в счётчики; в нашей базе нет
  ни столбца, ни байта, которым можно опознать читателя; повторный экспорт не
  отдаёт Matomo одни и те же строки дважды.

## Как устанавливать

Воспроизводимая инструкция — **`docs/server-setup-guide.md`, раздел 11**:
каталог для лога, пароли базы, блок `log` в Caddyfile с проверкой конфигурации,
запуск сервисов, мастер Matomo через ssh-проброс, токен импортёра, крон и
проверка. Здесь она намеренно не дублируется: две копии одних и тех же шагов
разъезжаются.

Как это выкладывалось в первый раз, с найденными по дороге граблями, — запись
`docs/deployment-log.md` от 2026-08-23.

## Что дальше

- **Доступ к дашборду без ssh — сделано 2026-08-24.** `stats.medinsky.net` под
  двумя замками: `basic_auth` в Caddy и вход Matomo. Порядок установки —
  `docs/server-setup-guide.md`, раздел 11.9.
- **Ретроспектива.** У nginx во frontend-контейнере накоплена история запросов
  без адресов, в формате `combined`. Её можно скормить Matomo тем же
  `import_logs.py` (формат он читает штатно) — тогда дашборд начнётся не с
  нуля. Проверить, насколько глубоко её сохранил docker:
  `docker inspect -f '{{.LogPath}}' redpen-frontend-1 | xargs ls -lh`.
- **Счётчики контента в кабинете.** Отчёт консольный, то есть доступен тому, у
  кого есть ssh. Грабли на этом пути: `/cabinet/` и `/app/` — обычная статика,
  nginx отдаёт их кому угодно; законный путь один — ручка `GET /api/stats/*` с
  проверкой роли.
